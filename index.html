QC assessment

The tool speeds up repeated work and evidence matching. It does not replace test design or final review.

QC analysis

Mismatches become visible during testing, without scanning raw logs. Each task result records who ran it, so AI runs and QC checks stay separate. One session covers only the rows it reached, not the full spec.

Limitations

  • Tracking validates only rows triggered during a session; the rest stay "not tested".
  • Results are only as good as the spec, which re-syncs from Lark every 60 seconds.
  • Rows whose valid value is free text typed by the user still need manual review.
  • AI-run results need QC review, and device runs need a device connected over ADB.

How it was tested

  • Cases 1–9 ran on the app's default config. Cases 10–12 changed Remote Config by writing the onboarding config into the debug build's config cache, and the real values were restored after testing.
  • "No ad" simulated by pointing the native request at a banner test unit so it fails with a format mismatch. A 1 ms timeout was tried first and did not work.
  • Every test ad looks the same, so ad swaps and reuse were checked from onAdImpression logs: unit and timestamp.
  • Compared with the previous build 1.0.2 on the same device to separate new defects from existing behavior.

Findings

FAILCase 10 · Severity High · reproduced 2/2
With swipe lock on, swiping on the full-screen ad page counts as an ad click and opens Play Store

Actions: clear data → swipe lock on → Language → Alt → OB1 → OB2 → Next → swipe right to left on the ad.

Expected: a locked swipe does nothing; only a tap counts as an ad click. Unintended clicks are an AdMob policy risk.

Edge case · Severity Low–Medium · 2/2
Tapping X just as the full-screen page auto-advances also counts as an ad click

Taps landing about 10 ms after the auto-advance opened Play Store. Taps from +14 ms on (8 tries) did not. Found by chance, then reproduced with timed taps.

QC assessment

Fix before swipe lock is enabled. A locked swipe must not create an ad click.

QC analysis

Evidence includes the expected behavior, the action sequence, the relevant log events and the observed navigation to Play Store. That supports investigating an interaction defect instead of relying on a screenshot alone.

Limitations

  • A single device and session do not establish broad device coverage or full regression reliability.
  • Agent-generated outcomes need human review when logs or UI observations are ambiguous.
CS-03 · Bug investigation

Coins lost after account deletion

IAP data integrity · real defect I found and reported · Android v1.1.2

IAPStateRemote ConfigData integrity
Risk
Deleting an account may unintentionally remove device-bound earned currency, causing user progress or balances to be lost.
Test condition
Restore config = false.
My responsibility
  • Found and reported the defect.
  • Wrote the steps, expected and actual results.
  • Recorded the screen evidence.
  • Listed the regression scope for the fix.
Expected behavior
Account-bound purchased coins are removed, while device-bound earned coins remain intact.
Observed behavior
Both balances are removed. After logging in again, the initial coin amount is granted again.

QC process

How I work through a feature

Risk decides what gets tested first. Every step leaves evidence someone else can check.

  1. 01

    Read the risks

    Find unclear rules, key journeys, money risks and data risks.

  2. 02

    Plan the tests

    Cover happy paths, errors, limits, state changes, interruptions and recovery.

  3. 03

    Run and record

    Test on real devices. Keep logs, screenshots and clear steps.

  4. 04

    Check the defects

    Compare expected and actual results. Confirm the impact, the reproduction rate and the regression scope.

  5. 05

    Give a QC assessment

    Report the tested scope, open defects, gaps and release risk, so the team can decide.
